## 铁律：根因调查未完成，不得提出修复

**在完成以下三件事之前，禁止提出或实施任何修复方案：**

### 1. 读全错误输出

不要只看异常类名或第一行就开始猜。

```
✅ 要求做到：
   - 从栈顶往下读到第一个非框架（业务代码）帧
   - 记录完整错误消息文本（含期望值/实际值、错误码）
   - 查看日志中该异常**之前**的上下文行（往往才是真正的线索）
   - 若有多条错误，判断哪条是首个（后续常是级联失败）

❌ 典型失败：
   看到 "TypeError: undefined" → 立刻写 `if (x) { ... }` 判空 → 掩盖了上游返回结构变更
```

### 2. 稳定复现

```
必须能回答："给我什么输入/状态/环境，我 100% 能触发它。"

- 无法复现 → 不进入修复阶段，先做复现工作：
  · 记录触发环境（OS、浏览器、Node/DB 版本、时区、并发度）
  · 缩小到最小复现用例（删掉一切无关代码，直到还能复现）
  · 间歇性故障：先加针对性日志/断言，把它变成可复现，再谈修复
- 复现一次都不成功却"按猜测修复"，等同于交付一个未验证的改动
```

### 3. 查近期变更

绝大多数缺陷由变更引入。先定位引入点，再定位根因：

```bash
# 谁、什么时候动了出错文件
git log --oneline -20 -- path/to/file.ts

# 出错行附近的 blame
git blame -L 80,110 path/to/file.ts

# 在两版本之间二分定位引入提交（revert 前先确认）
git bisect start HEAD <last-known-good>
git bisect run npm test -- --grep "failing test name"
```

**产出要求**：进入修复阶段前，必须能一句话说清"根因是什么、证据是什么"。说不清 = 调查未完成。

## 三振出局规则

```
第 1 次修复失败 → 说明假设不成立，回到根因调查，扩大证据收集
第 2 次修复失败 → 怀疑对系统边界的理解有误（并发？缓存？构建产物过期？环境差异？）
                   → 强制改变调查手段（加日志、抓包、profiling、读依赖源码）
第 3 次修复失败 → ⛔ 停止。不要尝试第 4 次修复。
```

### 为什么是三次

连续三次修复失败的含义是：**你的问题定位模型与真实系统不一致**。这种情况下第 4 次尝试的成功率并不比随机改动更高，而副作用（把代码改复杂、引入新缺陷、掩盖真实问题）持续累积。这通常指向架构层面的原因，而不是实现层面的原因。

> **"失败"以实际运行结果判定。** 改了代码但没有运行校验，既不算失败也不算成功——它是一次未完成的尝试，不计入三振计数（也不允许拿"改了没测"冒充一次尝试来凑数后草率收工）。

### 三振后的标准动作（上报，而非硬试）

```markdown
## 上报：三次修复失败，疑似架构/设计层问题

**症状**：[精确描述，含错误输出关键片段]
**复现**：[稳定复现步骤 / 最小用例]

**已尝试的三次修复**：
1. 假设 A（理由）→ 改动 X → 结果：仍失败，观察到 Y
2. 假设 B（理由）→ 改动 Z → 结果：错误形态变化为 W
3. 假设 C（理由）→ 改动 V → 结果：原问题消失但触发新失败 U

**三次失败共同指向**：[例如：状态被多处共享写入 / 初始化顺序不可控 /
  生命周期归属不清 / 同步接口承载了异步依赖]

**为什么我认为这不是实现问题**：[依据]

**建议下一步（需更高层决策）**：
- 选项 1：调整模块边界（影响范围、风险）
- 选项 2：改变数据流向（影响范围、风险）
- 选项 3：引入显式依赖注入替代隐式全局状态（影响范围、风险）

**我不会继续第 4 次修复，等待指示。**
```

- 主代理收到此类上报时，应升级给 `architect`（架构归因）或在阶段屏障处停下与用户确认方向，而不是换个代理继续第 4 次尝试。
- **禁止**把"三次失败"改写成"再试一次就好了"。

## 根因追踪：沿数据流反向追查

从错误现场出发，**逆着数据流向往上游走**，找到第一个被污染的值。修复点在污染源头，而不是污染被看见的地方。

### 追踪方法

```
错误现场（抛出异常 / 渲染出 undefined / 写坏数据库记录）
    ↓ 这个值是从哪来的？
上一层（函数参数 / 全局状态 / 环境变量 / DB 查询结果 / 网络响应 / 缓存）
    ↓ 它在这一层就已经错了吗？
    ├── 已错 → 继续往上游
    └── 此处变错 → 【污染点】= 第一个把正确值变成错误值的位置
    ↓
在污染点修复，而不是在错误现场加兜底判空
```

**判据**：为每个可疑层生成一个具体问题——"这一层拿到的值是什么类型/什么内容？"，用日志、断点、断言把答案取回来，而不是靠推理链猜到底。

```ts
// 追踪手段：给数据流打点，比读代码更有效
function setConfig(raw: unknown) {
  console.log('[trace] setConfig in:', raw, typeof raw);
  const cfg = normalize(raw);
  console.log('[trace] after normalize:', cfg);
  state.cfg = cfg;
  console.log('[trace] state.cfg assigned');
}
// 观察输出：哪一行之后值第一次变得不对 → 那一行之前就是污染点
```

### 反向追查的典型污染点

| 层级 | 常见污染源 |
|------|-----------|
| 入口 | 参数未校验 / 默认值在错误时机求值 / 序列化-反序列化丢类型 |
| 依赖 | 全局单例被别处写入 / 模块顶层副作用 / import 顺序 |
| 异步 | 竞态：读取发生在写入之前 / Promise 未 await / 闭包捕获旧值 |
| 缓存 | 失效条件缺失 / key 未包含影响结果的维度 / 跨请求共享可变对象 |
| 环境 | 时区、区域设置、路径分隔符、行尾符、大小写敏感文件系统 |
| 构建 | 产物过期、循环依赖、tree-shaking 掉副作用模块 |

## 污染源定位：测试互相影响时的二分法

**症状识别**：单个测试文件/用例独立运行通过，全量运行失败；或改变运行顺序后结果变化；或某测试"隔几次绿、隔几次红"而代码没动。这类问题几乎都是测试间的共享状态污染，而不是被测代码本身的缺陷。

### 定位步骤

```
1. 确认污染存在：全量跑（失败）vs 单跑（通过）
2. 缩小集合：只跑可疑子集（同目录/同文件/共享 fixture 的测试）
3. 二分定位污染源：把测试列表拆半，逐半与目标用例组合运行
4. 找到最小污染对：单个污染测试 + 受害测试
5. 修复隔离，而不是修复顺序
```

```bash
# 目标用例单独跑 → 通过
npx vitest run tests/b.spec.ts

# 全量跑 → b 失败，说明有前置测试污染了共享状态

# 二分：跑前半 + b
npx vitest run tests/a1.spec.ts tests/b.spec.ts     # 失败 → 污染源在前半
npx vitest run tests/a5.spec.ts tests/b.spec.ts     # 通过 → 排除 a5

# 逐个组合，最终锁定：
npx vitest run tests/a3.spec.ts tests/b.spec.ts     # 失败 → a3 是污染源
```

### 找到污染源后，修隔离（不修顺序）

| 污染形式 | 正确修法 | 错误修法 |
|---------|---------|---------|
| 修改全局变量 / `process.env` 未还原 | `afterEach` 还原快照 | 把 a3 挪到 b 后面 |
| 共享 mock（`jest.mock` 的返回值被累积修改） | 每个用例重新构造 mock 数据 | 在 b 里手动重置 mock |
| 数据库/文件系统残留 | 每个用例用独立事务并回滚，或独立临时目录 | 全量跑前先 `rm -rf` |
| 单例持有连接、计时器、订阅 | 用例结束显式 dispose/关闭 | 加 `--runInBand` 掩盖 |
| 时间相关（`Date.now`、定时任务） | 使用可控时钟（fake timers） | 加 `sleep` |

**结论口径**：报告时明确"这是测试隔离缺陷，不是产品缺陷"（或反之），避免把修复错误地落到生产代码上。

## 基于条件的等待：消灭 flaky 测试

**规则：等待条件成立，而不是等待固定时长。** 任何 `sleep(500)` 式硬编码等待都是 flaky 的来源：CI 慢时不够用，本地快时白等，且掩盖真实的时序依赖。

### 反例与正例

```ts
// ❌ 固定时长：CI 上偶发失败，本地永远通过（因为本地更快）
await new Promise(r => setTimeout(r, 300));
expect(screen.getByText('已保存')).toBeInTheDocument();

// ✅ 基于条件：轮询直到条件成立，或超时才失败（伪代码）
await waitFor(() => {
  // 条件：被等待的事实成立即返回
  expect(screen.queryByText('已保存')).not.toBeNull();
}, {
  timeout: 5_000,   // 超时上限 = 明确声明"最晚多久后认定失败"
  interval: 50,     // 轮询粒度，不是"睡一觉再放弃"
  message: '保存成功提示未在 5s 内出现',
});

// ✅ 有现成的可等待句柄时优先用它，而不是轮询 UI
await page.waitForFunction(
  () => document.querySelector('#report')?.dataset.ready === 'true',
  { timeout: 10_000 },
);

// ✅ 异步任务：等待它的完成信号（Promise / 状态转换），不猜时长
await queue.drain({ timeout: 3_000 });                        // 有可 await 的句柄
await waitFor(() => isSettled(queue), { timeout: 3_000 });    // 只有状态可查时轮询状态
```

> 上述 `waitFor` / `isSettled` / `queue.drain` 为**示意伪代码**，请按项目实际测试框架替换（如 Vitest/Jest 的 `waitFor`、Playwright 的 `waitForFunction` / `expect(...).toPass()`、Go 的 `assert.Eventually`）。要点不在函数名，而在"**等待条件是事实成立，而不是时间到**"。

### 编写要点

1. **必须显式超时**：无超时的条件等待会挂死；超时值是"最坏可接受时长"，不是"预期时长"。
2. **条件要断言"结果事实"**，而不是"某时刻存在某个中间态"。
3. **轮询间隔要小**：间隔是检测延迟，不是节流；把 timeout 设大、interval 设小。
4. **优先事件而非轮询**：能被 `await promise` / 状态回调 / 文件监听表达的，就不要轮询。
5. **失败信息可诊断**：超时时打印当前观察到的状态（实际值 vs 期望条件）。
6. **不要用固定等待"稳定" flaky**：加了 `sleep` 让测试变绿，只是把竞态推迟，缺陷仍在。

## 纵深防御：修复后的四层校验

**适用范围（按域分级）：**

- **debug 域（缺陷排查与修复）**：四层**全部执行**——修复单个点不足以宣称修复完成。修复后按四层依次校验；任何一层失败，都说明修复不完整或不正确，回到根因调查。
- **非 debug 域（新功能、重构、文档等）**：不需要机械跑满四层。执行**层 1（复现/单元测试）+ 与所触风险匹配的一层**即可：触及上下游契约（接口 / Schema / 共享模块）→ 加层 2；输入边界敏感 → 加层 3；改变用户实际路径 → 加层 4。

以下为四层的定义（debug 域全用；非 debug 域按上述规则选层）：

```
层 1：单元测试  —— 修复本身正确吗？
   针对根因写最小复现测试（应先失败于旧代码、通过于新代码）
   命令示例：npm test -- --grep "regression: <缺陷名>"

层 2：集成测试  —— 与上下游协作还正确吗？
   跑受影响模块的端到端链路，确认修复没有破坏调用方/被调用方的契约
   重点：真实 DB、真实 HTTP 客户端、真实文件系统（不要全用 mock 过关）

层 3：边界条件  —— 极端输入下还成立吗？
   空/null/undefined、0 与负数、超长、超大并发、重复提交、
   时区与夏令时、权限缺失、依赖超时与部分失败、幂等重放

层 4：真实场景  —— 用户实际路径上真的好了吗？
   按最初复现步骤在贴近生产的环境走一遍（真实数据量、真实浏览器/OS、
   真实网络抖动），而不是只看测试绿灯
```

### 校验记录要求

```markdown
## 验证
- [x] 层 1 单测：新增 `user.service.test.ts` 中 3 个用例，旧代码全部失败，新代码全部通过
- [x] 层 2 集成：`tests/api/user.spec.ts` 全绿（真实 Postgres）
- [x] 层 3 边界：空邮箱 / 255+ 字符 / 并发重复注册（幂等）均按预期
- [x] 层 4 真实场景：本地起服务，按原始复现步骤操作，缺陷不再出现
- [ ] 回归影响面：已检查 `getById` 的 4 个调用点，无行为变化
```

**只有层 1 通过就交付**是最常见的"修好了但线上还在坏"。若某层确实无法执行（缺环境、缺数据），必须在输出中显式声明未校验项与风险，而不是留白。

## 流程总览与检查清单

```
缺陷报告
   ↓
[1] 读全错误输出（完整栈、上文日志、首个错误 vs 级联错误）
[2] 建立稳定复现（最小用例；不可复现 → 先做可复现，不进入修复）
[3] 查近期变更（git log / blame / bisect 定位引入点）
[4] 反向追数据流，找到第一个被污染的值（污染点，不是错误现场）
[5] 判断是否为测试污染（单跑绿、全量红 → 二分定位污染源，修隔离）
[6] 最小修复：在污染点修，不做兜底掩盖
[7] 四层校验：单测 → 集成 → 边界 → 真实场景
[8] 记录根因与预防措施（防同类缺陷再发）
   ⛔ 任一次修复失败即回 [1]/[4] 重做调查；连续三次失败 → 停止并上报，禁止第 4 次尝试
```

### 开工检查

- [ ] 已读完整错误输出（含异常前的上下文行）
- [ ] 已有稳定复现步骤或最小复现用例
- [ ] 已检查近期变更并定位引入点
- [ ] 已确定污染点（并能说出证据）

### 收工检查

- [ ] 修复落在污染点，而非在错误现场加判空/try-catch 掩盖
- [ ] 已按适用层级校验并记录各层结果（debug 域：四层全跑；非 debug 域：层 1 + 与所触风险匹配的层）
- [ ] **每条"已通过"都对应本消息内实际运行过的命令与其完整输出**——凭改动内容推断"应该没问题"不算校验（验证铁律：文字描述不是证据）
- [ ] 未通过校验的层已显式声明
- [ ] 新增回归测试（旧代码失败、新代码通过）
- [ ] 已写出根因说明与预防措施
- [ ] 未做超出缺陷范围的"顺手重构"
- [ ] 若三次失败：已停止并输出架构层上报，未发起第 4 次尝试
