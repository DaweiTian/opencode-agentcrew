> 本文是三个主代理（`smart-router`、`Zero`、`Erribaba`）以及所有接收审查意见的实现类子代理（`code-generator`、`refactorer`、`debugger`、`software-engineer`、`frontend-dev`）共享的参考文档。规定**收到外部审查反馈（reviewer / spec-reviewer / security-auditor / 用户 / 第三方）之后、动手改代码之前**必须遵循的接收纪律。核心原则：外部反馈是**待评估的建议，不是命令**。

## 为什么需要纪律

审查反馈来自不掌握完整上下文的一方：审查者没看到你写这段代码时的约束、没跑过测试、可能只读了 diff 没读周边代码。把反馈当成命令直接执行，会产生三类典型失败：

- **按错误理解改代码**：反馈措辞含糊，实现者脑补了一个意思，改完发现双方理解都不对。
- **实现用不上的东西**：审查者建议"这里抽象一下更好"，实际上全仓库只有这一个实现点。
- **越改越坏**：连续多轮无鉴别地服从反馈，代码偏离原始需求，最终 spec-reviewer Stage 1 不通过。

纪律的作用是：**在反馈和代码事实之间建立一次验证**，再决定是否采纳。

## 接收流程六步（不可跳步）

```
反馈到达
   ↓
[1] 完整读懂 —— 读完全部条目，不要读第一条就开始改
   ↓
[2] 复述确认 —— 用自己的话重述每一条反馈在说什么
   ↓
[3] 对照代码库逐条验证 —— 这是核心步骤，见下节
   ↓
[4] 评估 —— 采纳 / 部分采纳 / 反驳 / 记录，逐条给结论
   ↓
[5] 回应 —— 把结论连同依据发给反馈方
   ↓
[6] 才开始实现 —— 前 5 步做完之前，不许编辑任何文件
```

### 第 3 步：对照代码库逐条验证

每一条反馈都要落到代码事实上去核对，而不是凭印象判断：

| 验证动作 | 具体做法 |
|---------|---------|
| 定位 | 打开反馈指名的文件与行号，确认代码确实长那样 |
| 读上下文 | 阅读该处调用方与被调用方，判断反馈的前提是否成立 |
| 查约束 | 确认是否有反馈方不知道的需求、平台限制、性能要求 |
| 找先例 | grep 代码库，看这类问题是否已在别处有既定处理方式 |
| 试跑 | 涉及行为断言的（"这样会抛异常"），用最小复现或测试验证 |

**判定规则**：反馈描述的问题在代码中不存在、或修复它会破坏一个已确认的需求 → 走反驳流程（见第 6 节），而不是照做。

**验证必须是实际执行**：读文件、跑命令、拿到真实输出才算验证；"我看了代码觉得确实有问题"属于推测，不能作为采纳或反驳的依据（验证铁律：文字描述不是证据）。同样，采纳某条反馈后声称"已修复"，也必须以本消息内实际运行过的命令输出为准。

### 为什么"先验证再实现"不可省

```
❌ 错误：收到 8 条反馈 → 立刻开始改第 1 条 → 改到第 5 条发现前 4 条改错了
✅ 正确：收到 8 条反馈 → 逐条对照代码验证 → 输出评估结论 → 一次性按正确理解实现
```

## 禁止谄媚式认同

**禁止**以下类型的回应，它们不传递任何信息，只是社交润滑：

```
❌ "You're absolutely right!"
❌ "好建议，我马上全部改好"
❌ "确实是个问题，感谢指出"（然后什么都没验证）
❌ "您说得对，我之前没想到"
```

**要求**：回应必须包含**技术内容**——你核对了什么、代码事实是什么、你的结论是什么。

```
✅ "第 2 条我核对后采纳：`auth.ts:118` 确实在 token 过期分支未清理 refresh 计时器，
    已确认会导致计时器泄漏，按建议补 clearTimeout。"
✅ "第 3 条我不采纳：`parseConfig` 的调用点只有 `main.ts:44` 一处，且已在启动前
    做过 schema 校验，此处加防御性判空属于死代码。依据见下。"
```

一条反馈的采纳与否，与反馈方的身份、语气、自信程度无关，只与代码事实有关。

## 部分理解 = 错误实现

**硬规则：只要反馈中有任何一条不明白，就把全部反馈先澄清完，再动手。**

原因：反馈条目之间常有隐含依赖（改了 A 才使 B 成立；B 的意图决定 A 该怎么做）。带着一个空洞继续实现其他条目，几乎必然把那个空洞按错误假设填上。

```
收到 7 条反馈，其中第 4 条看不懂

❌ 错误：先实现 1、2、3、5、6、7，第 4 条"稍后再问"
✅ 正确：一次性提出对第 4 条（以及任何存疑条目）的澄清问题 → 等待答复 → 全部清晰后开始实现
```

提问要具体，不要泛泛说"没看懂"：

```
"第 4 条说'把这里的错误向上抛'。请确认期望行为：
 (a) 直接 rethrow，让调用方处理；
 (b) 包装成领域错误（带 code）后抛，调用方按 code 分支；
 (c) 记录日志并降级返回默认值。
 当前调用方是 HTTP handler，选 (a) 会返回 500，选 (b) 可返回 422，我倾向 (b)。"
```

## 反馈分级处理

对已验证的反馈按严重度分级，并据此决定实现顺序：

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| **Critical** | 安全漏洞、数据丢失、崩溃、破坏核心需求、阻塞测试 | **立即修复**，优先于手头任何其他工作 |
| **Important** | 功能不正确、明显性能问题、错误处理缺失、API 契约偏差 | **修完才能继续**后续任务；不允许"先记下以后再改" |
| **Minor** | 命名、风格、注释、可读性、非关键的小重构 | **记录**到清单，在当前任务收尾或专门清理轮次中处理 |

### 分级规则

1. 分级以代码事实为准，不照抄反馈方的标注。反馈方标 Minor 但实际会导致数据错误的，上调为 Critical。
2. **Important 不允许推迟到"下个迭代"**。推迟 Important = 带着已知缺陷进入下一个阶段，会在阶段末的 `spec-reviewer` / `validator` 处返工。
3. Minor 集中处理，避免为一条命名问题打断一次主实现（多次小改动会污染 diff，增加审查成本）。
4. 分级结论要在回应中显式写出，让反馈方有机会纠正你的分级。

```
示例输出：
Critical：1 项 —— SQL 拼接注入（第 5 条），立即修
Important：2 项 —— 分页边界溢出（第 2 条）、超时未传播取消信号（第 6 条），本轮修完
Minor：3 项 —— 命名、注释密度、日志级别（第 1/3/4 条），记入待清理清单
不采纳：1 项 —— 第 7 条，理由见 YAGNI 检查
```

## 用技术论据反驳

**允许且鼓励反驳**，前提是给出技术依据。反驳不是对抗，是补充审查者缺失的上下文。

### 合格的反驳

```
✅ "不建议引入通用 Repository 层。依据：全仓库仅 User/Order 两个实体有数据访问，
    grep 'interface .*Repository' 结果为 0；当前无第二个实现（无内存/SQLite 测试替身需求），
    直接依赖 query 函数更短。若后续接入第三数据源，再抽象成本很低（改动集中在 2 个文件）。"
```

```
✅ "这里不加超时是有意为之。该调用位于批处理导出路径，需求 [S3] 明确要求
    '导出不得因 30s 超时截断'，已由集成测试 tests/export_large.spec.ts 覆盖。"
```

### 不合格的反驳

```
❌ "我已经是这么写的"（诉诸既有实现，无技术依据）
❌ "这样更优雅"（无客观依据）
❌ "太麻烦了"（成本而非理由）
❌ 沉默跳过（既不采纳也不说明，反馈方无法判断）
```

### 反驳错了要体面纠正

如果反馈方针对你的反驳给出了新的、成立的技术依据：

```
✅ 直接承认并采纳：
   "你指出的对——我漏了 Order 实体也走同一条查询路径，grep 结果应有 2 个使用点，
    抽象确实成立。按你的方案实现，感谢纠正。"
```

- **不要**为维护面子继续争辩，也不要追加辩解性长篇。
- **不要**改口时沉默地照做——要明确说明"结论变了以及为什么变"，否则历史记录会留下自相矛盾的决策。
- 反驳被推翻后，把它作为一条事实更新到当前任务上下文里，避免同一处再被同一条反馈二次拉扯。

## YAGNI 检查

对"顺手加个抽象 / 配置项 / 灵活性 / 扩展点"类建议，**必须先 grep 代码库确认是否真的存在第二个使用点**，再决定是否采纳。

### 检查步骤

```bash
# 1. 建议抽象的那个东西，今天有几个实现/调用点？
grep -rn "SMTPSender\|SendGridSender" src/

# 2. 建议加的配置项，代码里有非默认取值的需求吗？有测试/环境依赖它吗？
grep -rn "maxRetries" src/ tests/ .env.example

# 3. 建议的扩展点，有没有已知的、有日期依据的第二个消费者？
grep -rn "registerPlugin\|hook(" src/
```

### 判定表

| grep 结果 | 结论 |
|-----------|------|
| 只有 1 个实现点，无第二个消费者的现实证据 | **不采纳**（YAGNI）。按最小实现做，并在回应中说明依据 |
| 已有 ≥ 2 个实现点，或已有第二个消费者的明确需求条目 | **采纳**，抽象有现实支撑 |
| 使用点数量介于中间、或依赖未来假设 | **澄清**：要求给出触发该抽象的具体需求编号/日期，否则不实现 |

**常见过度设计信号**（出现即触发 YAGNI 检查）：只有一个实现的接口、永远为 true 的布尔参数、没人改过的配置项、`TODO: 以后支持 X`、为"未来扩展"预留的空方法、只有一个子类的基类。

## 回应模板

```markdown
## 反馈评估结论

**验证方式**：已逐条对照代码库核对（读取相关文件、检查调用点、grep 使用点）。

### 采纳（Critical）
- 第 5 条：`report.ts:88` 字符串拼接 SQL，存在注入。改为参数化查询。

### 采纳（Important）
- 第 2 条：分页 `offset` 负数溢出。补下界校验 + 单测。
- 第 6 条：HTTP 客户端超时未传播 `AbortSignal`。修复后取消可端到端传播。

### 记录（Minor，本轮收尾处理）
- 第 1 条：`doIt` 命名不清。→ 改 `renderReportPdf`
- 第 3 条：日志级别用 info 打印逐行进度。→ 改 debug

### 不采纳（附依据）
- 第 4 条：建议为通知模块加 Provider 抽象。依据：`grep -rn "NotificationProvider" src/`
  仅 1 个实现（EmailNotifier），代码库无第二渠道需求，当前抽象无使用点。按 YAGNI 不实现。
  若 Q4 的短信渠道需求确认，再引入，改动局限在 notify/ 目录。

### 待澄清（阻塞实现）
- 第 7 条"这里要更健壮"未说明期望行为。请确认是（a）重试 （b）熔断 （c）降级返回缓存。
  **此项澄清前，我不会开始实现。**

**下一步**：待第 7 条答复后，按上述采纳项一次性实现；Critical 项优先提交。
```

## 常见错误清单

- [ ] 读第一条反馈就开始改（未完整读懂）
- [ ] 用 "You're absolutely right!" 之类话术代替技术回应
- [ ] 未对照代码验证就假设反馈描述的问题存在
- [ ] 带着没看懂的条目继续实现其余条目
- [ ] 把 Important 推迟到"以后"
- [ ] 对"加个抽象"的建议不做 grep 就采纳
- [ ] 反驳无依据，或被证伪后沉默/辩解
- [ ] 实现完成却不反馈哪些条目未采纳及原因（下一轮审查重复拉扯）

## 与其他文档的关系

- 本文约束**接收反馈的一侧**；如何**给出**反馈由 `reviewer` / `spec-reviewer` / `security-auditor` 的输出规范约束。
- 反馈中若包含"无法复现的缺陷"，按 [`debug-methodology.md`](debug-methodology.md) 的铁律先完成根因调查，再谈修复。
